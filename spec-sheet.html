Sentry Access 1.6 - spec sheet

Deployment architecture, hardware requirements, security model, and current limitations. Prepared for security integrators, MSSPs, and client technical reviewers.

Document revision 1.6 · November 2026 · Print or save as PDF

Pricing Ask a technical question

1. Intended use

Sentry Access is a local-first biometric access-control application for commercial single-site deployments. It performs 1:N face verification at a Windows kiosk, evaluates local access policy, and pulses a door relay only after identity and policy both pass. An optional RTSP camera gateway logs observations of already-enrolled identities, and an optional LAN hub consolidates identity and audit data for an iPhone companion.

It is not a certified life-safety system, an emergency-egress product, or a substitute for code-compliant door hardware. It is also not a general-purpose surveillance or people-tracking platform.

2. System architecture

Kiosk hostWindows 10 or 11, x64. Electron desktop application with an isolated renderer and constrained preload bridge.
Face engineLocal SSD face detector, 68-point landmarks, FaceNet 128-dimensional descriptor. Matching runs on the kiosk.
Template storageAES-GCM encrypted templates in local application storage. Master key protected by the Windows OS keystore (DPAPI through Electron safeStorage).
Door controlElectron main process driver. Axis VAPIX I/O port management or generic HTTP relay. Credentials in the OS keystore.
Camera gatewayBundled FFmpeg decodes RTSP/RTSPS/HTTP streams to JPEG frames for local face matching. No frame storage.
Local auditIndexedDB on the kiosk; CSV export; optional sync queue with retry.
Hub (optional)Fastify API + PostgreSQL on the customer LAN. Device registration, signed identity bundles, delta sync, audit ingestion, mobile pairing, mDNS discovery.
Companion (optional)iOS app, read-only audit and kiosk inventory. Keychain token, SQLite cache, Face ID lock.

3. Identity and biometrics

  • Enrollment captures a live face sample, applies a quality gate, and stores a 128-float descriptor encrypted with AES-GCM.
  • Verification runs 1:N against locally hydrated templates. The default Euclidean distance threshold is 0.50 and is configurable.
  • Liveness uses a random blink or head-turn challenge. This is a basic gate, not certified presentation-attack detection.
  • Roles are directory metadata: Employee, Contractor, Visitor, Administrator. Door rules can require specific roles.
  • No raw images or video are retained by the kiosk. The audit record contains identity metadata, decision, score, door or camera label, and timestamps.
  • Unknown faces are not identified or logged by the camera gateway.

4. Door control

Axis controllersAXIS A1210, A1601, A1610 class network door controllers with AXIS OS 9.70 or later and the I/O port management API.
AuthenticationHTTP Basic or Digest. Use a dedicated operator account with the minimum privileges required for I/O control.
Relay behaviorConfigurable I/O port, 1–30 second pulse, active state open or closed. Default sequence: active for N seconds, then idle.
Generic relayHTTP POST with a JSON body containing door ID, name, port, and unlock seconds. Optional Basic or Digest authentication.
PolicyWeekly windows, multiple windows, overnight windows, holidays, allowed roles, and a kiosk door binding. Missing or invalid policy fails closed.
Manual overrideAvailable from the Doors page for commissioning. Bypasses role and schedule checks and is written to audit as a door command.
Not includedREX/door-position supervision, held/forced-door alarms, anti-passback, two-person rule, interlock, elevator control, and fire-release integration.

5. Camera gateway

  • Inputs: RTSP, RTSPS, HTTP MJPEG, and NVR channel URLs. FFmpeg is bundled with the installer.
  • Sampling: 2 frames per second per camera at a configurable working width (default 960 px).
  • Recognition: single-face detection per sampled frame, matched against enrolled templates.
  • Logging: matched enrolled identities only, with a 60-second per-camera/per-identity cooldown.
  • Background mode: closing the window minimizes to the system tray while cameras are active.
  • Not included: automatic ONVIF discovery, continuous recording, live view, PTZ, audio, LPR, and Ring.

6. Audit, sync, and mobile

  • Event types: access decision, camera observation, and manual door command.
  • Fields include identity, employee ID, role, decision, confidence, distance, threshold, reason, provider, camera/door labels, and timestamps.
  • Hub events are stored in PostgreSQL and exposed to the site-scoped mobile API.
  • Identity sync uses ECDSA-signed bundles. Device authentication uses a bearer token; per-event device signatures and hash-chaining are not yet implemented.
  • The iOS companion is read-only and does not perform recognition or ingest camera streams.
  • CSV export is available from the desktop audit view.

7. Security model

  • Renderer Node integration is disabled; context isolation and Chromium sandboxing are enabled.
  • The app is served through a private custom protocol with a production CSP. External navigation is blocked.
  • Biometric templates and credentials are encrypted at rest. The raw master key never enters the renderer.
  • Controller, camera, and sync credentials are excluded from audit payloads and mobile data.
  • Door decisions are made locally and fail closed on controller error or policy failure.
  • The installer is currently unsigned. Code signing, secure auto-update, operator accounts/RBAC, and per-event signing remain on the roadmap.

8. Deployment requirements

KioskWindows 10/11 x64, 8 GB RAM minimum, 16 GB recommended, SSD, webcam, stable power. Wired Ethernet recommended.
NetworkKiosk must reach the Axis controller and camera/NVR streams. Prefer an isolated camera VLAN and a read-only camera account.
Door hardwareFail-safe strike, independent request-to-exit, door position sensor (recommended), fire-alarm release, and adequate power/UPS.
HubAlways-on Windows or Linux host with PostgreSQL. Backups stored on encrypted media.
MobileiPhone with a signed Sentry Companion build. Pairing requires the hub on the same network or a reachable hub URL.

9. Commissioning checklist

  • Confirm written authorization for the cameras and biometric deployment.
  • Verify controller credentials with the built-in test and confirm the port is an output.
  • Test an authorized role, an unauthorized role, a closed schedule, and a holiday.
  • Disconnect the controller and confirm the decision is denied and audited.
  • Confirm mechanical egress works with the software powered off.
  • Pair the iPhone, verify audit delivery, then export a CSV and take a hub backup.
  • Record the site’s retention period, consent process, and deletion request procedure.

10. Current limitations

  • Not certified to UL, EN, SOC 2, ISO 27001, or any access-control standard.
  • Axis integration has been validated against a simulated VAPIX endpoint, not yet a physical controller in this build.
  • No REX/door-position supervision, held/forced-door alarms, anti-passback, two-person rule, or interlock.
  • Manual unlock is not bound to an authenticated operator identity.
  • No automatic ONVIF discovery, Ring support, live view, recording, PTZ, audio, or license-plate recognition.
  • Basic challenge-response liveness; no certified PAD or anti-spoofing.
  • No server admin UI, RBAC, mobile-token revocation UI, rate limiting, or immutable audit log.
  • Windows installer unsigned; iOS distribution requires an Apple signing identity.
  • Biometric consent, signage, retention, DPIA, and deletion obligations remain with the deploying organization.

11. Licensing and support

Licensing is perpetual and per site, not per user. Starter includes one kiosk, two doors, four camera streams, and local audit. Pro adds the LAN hub, four kiosks, four doors, eight camera streams, and five mobile seats. Capacity packs add doors, camera streams, or mobile seats without a new contract or reinstall. The optional annual plan covers major upgrades, encrypted off-site backup, and priority commissioning support. Hardware, installation, travel, and taxes are separate.

Current pricing is published at the pricing section. Multi-site and 10+ door terms are quoted directly. Licenses are ECDSA-signed offline files and are verified locally by the kiosk and hub.
